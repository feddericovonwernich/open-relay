Technical dossier / 2026 design

One factual notification, assembled once.

The GitHub connector owns the facts it already has, turns them into bounded evidence, and emits a deterministic notification only when the observation is eligible. Relay owns durability and delivery; no model interprets repository data.

Purpose
Make review state, CI conclusions, and configured automation actionable through one repeatable path.
Not in scope
No speculative projection engine, duplicate discovery boundary, or new interpretation of untrusted comment text.

Chapter 01 / ownership

One factual notification

The GitHub connector is the first producer because it already owns authentication, current-head discovery, evidence snapshots, final-head fencing, and per-PR observation state.

That ownership keeps the first notification factual rather than inferential. REST supplies the pull request and checks; GraphQL supplies review threads. The connector combines those observations with configured provider identities, applies the design's fixed rules, and hands Relay a generic event. Existing low-level events remain available to other consumers instead of being replaced by a new abstraction.

Review invariant Existing low-level events remain additive and unchanged.

Chapter 02 / enablement

Dormant until identities are explicit

Verification is opt-in and valid only for combined repositories with configured reviewer logins and, where required, an explicit GraphQL URL.

Generated contracts can exist without being active. Setup discovers the repository mode, provider identities, reviewer logins, and process supervision before analysis is enabled. Missing or malformed configuration is a boundary failure, not an invitation to guess. This makes an operator's decision visible and prevents an incomplete identity map from becoming a false all-clear.

Review invariant Missing or malformed evidence is never interpreted as an all-clear.

Chapter 03 / evidence

Resolved means GitHub says resolved

Review findings come from PullRequestReviewThread.isResolved and the root comment author, with deterministic pagination, truncation, counts, and evidence digesting.

GraphQL pagination is bounded and explicit. A thread matches a configured provider by its root author; its resolution state is read from GitHub's authoritative field, not inferred from comment prose. The connector preserves enough evidence for an action without another discovery query, while payload bounds keep the event suitable for transport and replay. Comment bodies remain data even when they contain instructions.

Review invariant Comment bodies are untrusted data, never instructions.

Chapter 04 / verdict

Fixed rules, reviewable outcomes

Terminal Check Runs, unresolved configured-provider threads, and ambiguous neutral Bugbot results map to a closed action set.

The decision boundary is intentionally small. Failed CI, unresolved review findings, and the specified neutral Bugbot ambiguity become action items; an all-clear result has an empty action list. The same raw evidence therefore has one verdict, and the payload records the rule-shaped outcome instead of asking a model to explain it.

Review invariant verdict = actions.length === 0 ? success : action_required.

Chapter 05 / settlement

Stable evidence before emission

Continuous mode waits for two identical eligible observations; one-shot mode reconciles immediately. Both apply the final head fence and canonical payload identity.

Continuous polling records an observation, waits for terminal evidence, and requires the next eligible observation to match before emitting. A changed head resets that observation. One-shot mode takes the eligible snapshot immediately, while the same canonical identity makes restart replay idempotent. Resolution or edits can change the evidence digest at the same head, so a stable, distinct identity may produce a new notification rather than being suppressed as a duplicate.

Review invariant A changed head resets observation; an accepted same-head identity never reposts in process state.

Chapter 06 / durability

Print, then acknowledge

A notification-only worker path claims one correlation-scoped event, prints one JSON line, and completes internally only after stdout succeeds.

relay notify hides registration and leasing from the connector. A single consumer claims the event, writes the notification, and acknowledges only after the write succeeds. If the process crashes before completion, the lease can be replayed; this is at-least-once delivery by construction. Silent loss is not traded for a misleading exactly-once promise.

Review invariant Delivery is at least once; silent loss is forbidden.

Chapter 07 / resilience

Failure stays in its lane

GraphQL errors, invalid verification mappings, Relay outages, and head drift isolate unified verification without suppressing configured automation or generic CI events.

Authentication is connector-fatal because no trustworthy source can exist without it. Other failures are narrower: a GraphQL error affects the repository verification path; a Relay outage remains retryable; head drift suppresses a stale unified event. Sibling repositories and low-level events continue, so one incomplete evidence path cannot stop unrelated automation.

Review invariant Authentication remains connector-fatal; other failures stay repository- or path-scoped.

Chapter 08 / seam

A seam, not an engine

The event and notification contracts remain generic enough for a future durable aggregation family, but no projection engine is built without a second use case.

Correlated low-level events can later feed a typed durable reducer without changing the generic delivery contract. That possibility is a boundary, not a reason to invent machinery now. The first producer stays connector-owned, and any migration must preserve explicit versions, identity, and delivery semantics so the future path can be reviewed against the same facts.

Review invariant Migration requires a new version or explicitly preserved producer and idempotency semantics.
