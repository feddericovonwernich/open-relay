Technical dossier / 2026 design

The connector assembles one factual notification.

The GitHub connector owns the facts. It converts the facts into bounded evidence. It emits a deterministic notification only for an eligible observation. Relay provides durable delivery. No model interprets repository data.

Purpose
Show review state, CI conclusions, and configured automation in one repeatable path.
Not in scope
The design does not add a projection engine, a second discovery boundary, or an interpretation of untrusted comment text.

Chapter 01 / ownership

One factual notification

The GitHub connector is the first producer. It owns authentication, current-head discovery, evidence snapshots, final-head fencing, and per-PR observation state.

This ownership keeps the notification factual. REST supplies pull request data and checks. GraphQL supplies review threads. The connector combines this evidence with configured provider identities. It applies fixed rules and sends a generic event to Relay. Other consumers can continue to use low-level events.

Review invariant Low-level events remain available and unchanged.

Chapter 02 / enablement

Dormant until identities are explicit

Verification is optional. A combined repository must define reviewer logins. The configuration must also define a GraphQL URL when the connector requires one.

Generated contracts can remain inactive. Setup finds the repository mode, provider identities, reviewer logins, and process supervision. Setup enables analysis only after it finds these values. Missing or malformed configuration causes a boundary error. This rule shows the operator's decision and prevents a false all-clear from an incomplete identity map.

Review invariant The connector never treats missing or malformed evidence as an all-clear.

Chapter 03 / evidence

GitHub supplies the resolution state

The connector reads review findings from PullRequestReviewThread.isResolved and the root comment author. It uses deterministic pagination, truncation, counts, and evidence digests.

The connector bounds GraphQL pagination. It matches a thread to a configured provider by the root comment author. GitHub's isResolved field supplies the resolution state. The connector does not infer resolution from comment text.

The connector keeps enough evidence to act without another query. Payload limits keep the event suitable for transport and replay. Comment bodies remain data even if they contain instructions.

Review invariant Treat comment bodies as untrusted data, not as instructions.

Chapter 04 / verdict

Fixed rules produce one verdict

Terminal Check Runs, unresolved configured-provider threads, and ambiguous neutral Bugbot results map to a fixed action set.

The decision rules are small and fixed. Failed CI, an unresolved review finding, and an ambiguous neutral Bugbot result each create an action. An all-clear result has no actions. The same evidence always produces the same verdict. The payload records that verdict. A model does not explain the evidence.

Review invariant verdict = actions.length === 0 ? success : action_required.

Chapter 05 / settlement

Stable evidence before emission

Continuous mode requires two identical eligible observations. One-shot mode evaluates immediately. Both modes use a final head fence and a canonical payload identity.

Continuous polling records an observation. It waits for terminal evidence. It emits only after the next eligible observation matches. A changed head resets the observation.

One-shot mode evaluates the eligible observation immediately. Both modes use the same canonical identity. This identity makes restart replay idempotent. A resolved or edited thread can change the digest at the same head. Continuous mode then requires two stable observations of the new identity. One-shot mode does not wait.

Review invariant A changed head resets the observation. The process does not post an accepted same-head identity again.

Chapter 06 / durability

Print precedes completion

The notification worker claims one event for one correlation. It prints one JSON line. It completes the event only after stdout succeeds.

relay notify hides registration and leasing from the connector. One consumer claims the event. It prints the notification. It completes the event only after the print succeeds.

If the process crashes before completion, the lease expires and Relay can replay the event. This process gives at-least-once delivery. It does not claim exactly-once delivery.

Review invariant Delivery is at least once. The worker must not lose an event silently.

Chapter 07 / resilience

Failures remain isolated

GraphQL errors, invalid verification mappings, Relay outages, and head drift affect only unified verification. Configured automation and generic CI events continue.

The connector stops if authentication fails. Without authentication, the connector cannot trust the source. A GraphQL error affects only that repository's verification path. A Relay outage delays delivery. Head drift suppresses a stale unified event. Sibling repositories and low-level events continue.

Review invariant An authentication failure stops the connector. Other failures remain repository- or path-scoped.

Chapter 08 / future aggregation

Future aggregation remains optional

The event and notification contracts can support a future durable aggregator. The design does not add a projection engine before a second use case exists.

A future typed durable reducer can consume correlated low-level events. It can reuse the notification delivery contract. The current design defines only this boundary. The connector remains the first producer. A migration must preserve or version the producer, identity, and delivery rules.

Review invariant A migration must create a new version or preserve producer and idempotency rules.
