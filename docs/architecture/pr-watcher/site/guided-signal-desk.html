01 / system boundary

One factual notification

The GitHub connector is the first producer. It owns authentication, current-head discovery, evidence snapshots, final-head fencing, and per-PR observation state. Setup remains inactive until the operator defines repository mode, provider identities, reviewer logins, and process supervision.

Review question Does the correct boundary own each input?

  • Does the connector use its current-head data without a second query?
  • Must the operator define every required identity before analysis starts?

Invariant: Low-level events remain available and unchanged.

02 / evidence

GitHub supplies the resolution state

The connector reads review findings from PullRequestReviewThread.isResolved and the root comment author. It uses deterministic pagination, truncation, counts, and evidence digests. It treats comment bodies as data, not as instructions.

Review question Does the payload contain enough bounded evidence to act without another query?

  • Does the connector match a provider by the root comment author?
  • Do pagination, truncation, counts, and the digest remain stable for the same evidence?

Invariant: The connector treats comment bodies as untrusted data, not as instructions.

03 / decisions

Fixed rules produce one verdict

Fixed rules map terminal Check Runs, unresolved configured-provider threads, and ambiguous neutral Bugbot results to a fixed action set. A model does not interpret GitHub data.

Review question Can the same evidence produce different verdicts?

  • Can you trace each terminal result to one action or an all-clear result?
  • Does an ambiguous neutral result create an action?

Invariant: verdict = actions.length === 0 ? success : action_required.

04 / settlement

Stable evidence before emission

Continuous mode requires two identical eligible observations. One-shot mode evaluates immediately. Both modes use a final head fence and a canonical payload identity. A changed head resets the observation.

Review question Which evidence changes the identity? Which transient failures only delay settlement?

  • Can a pending check or head drift cause emission before the final head fence?
  • Do success, action-required, one-shot, and replay paths use the same canonical identity?
  • Can a resolved or edited thread produce a new notification for the same head?

Invariant: A changed head resets the observation. The process does not post an accepted same-head identity again.

05 / delivery

Print precedes completion

The notification worker claims one event for one correlation. It prints one JSON line. It completes the event only after stdout succeeds. relay notify hides registration and leasing.

Review question What happens if the process crashes before or after the print?

  • Does a crash before completion keep the event available for replay?
  • Can one claim print duplicate output?
  • Can completion discard an event without output?

Invariant: Delivery is at least once. The worker must not lose an event silently.

06 / resilience

Failures remain isolated

GraphQL errors, invalid verification mappings, Relay outages, and head drift affect only unified verification. Configured automation and generic CI events continue.

Review question Can one failed repository stop a sibling repository? Can one failed evidence source stop low-level events?

  • Which failure stops the connector?
  • Which failures remain repository- or path-scoped?
  • Does Relay retry delivery without changing low-level events?

Invariant: An authentication failure stops the connector. Other failures remain repository- or path-scoped.

07 / future aggregation

Future aggregation remains optional

The event and notification contracts can support a future durable aggregator. The design does not add a projection engine before a second use case exists.

Review question Can the first producer support migration without speculative code?

  • Can a later durable reducer consume correlated events and reuse delivery?
  • Which producer and idempotency rules must a migration preserve or version?

Invariant: A migration must create a new version or preserve producer and idempotency rules.
