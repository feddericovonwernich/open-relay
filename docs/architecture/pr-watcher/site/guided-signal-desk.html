01 / system boundary

One factual notification

The GitHub connector is the first producer because it already owns authentication, current-head discovery, evidence snapshots, final-head fencing, and per-PR observation state. Setup stays dormant until repository mode, provider identities, reviewer logins, and process supervision are explicit.

Reviewer question Is any input duplicated or trusted by the wrong boundary?

  • Can the connector produce one factual observation without asking a second component to rediscover the head?
  • Can an operator enable analysis without pinning every identity it depends on?

Invariant: Existing low-level events remain additive and unchanged.

02 / evidence

Resolved means GitHub says resolved

Review findings come from PullRequestReviewThread.isResolved and the root comment author, with deterministic pagination, truncation, counts, and evidence digesting. Comment bodies are data, never instructions.

Reviewer question Does the payload preserve enough bounded evidence for action without another discovery query?

  • Does provider matching use the root author rather than an untrusted reply?
  • Are pagination, truncation, counts, and the digest stable when GitHub returns the same evidence?

Invariant: Comment bodies are untrusted data, never instructions.

03 / decisions

Fixed rules, reviewable outcomes

Terminal Check Runs, unresolved configured-provider threads, and ambiguous neutral Bugbot results map to a closed action set. No model interprets GitHub data.

Reviewer question Can the same raw evidence ever produce two verdicts?

  • Can every terminal result be traced to one deterministic action or to an explicit all-clear?
  • Does an ambiguous neutral result remain visible instead of being mistaken for success?

Invariant: verdict = actions.length === 0 ? success : action_required.

04 / settlement

Stable evidence before emission

Continuous mode waits for two identical eligible observations; one-shot mode reconciles immediately. Both apply the final head fence and canonical payload identity. A changed head resets observation, while an accepted same-head identity never reposts in process state.

Reviewer question Which late evidence changes the identity, and which transient failure only delays it?

  • Can a pending check or head drift create an emission before the final fence?
  • Do success, action-required, one-shot, and replay paths agree on canonical identity?
  • Can a resolved or edited thread create a distinct same-head notification after stability?

Invariant: A changed head resets observation; an accepted same-head identity never reposts in process state.

05 / delivery

Print, then acknowledge

A notification-only worker path claims one correlation-scoped event, prints one JSON line, and completes internally only after stdout succeeds. Relay registration and leasing remain behind relay notify.

Reviewer question What happens at each crash point around printing and completion?

  • Can a crash before stdout acknowledgment leave an event available for replay?
  • Can one claim produce duplicate output, or can completion silently discard it?

Invariant: Delivery is at least once; silent loss is forbidden.

06 / resilience

Failure stays in its lane

GraphQL errors, invalid verification mappings, Relay outages, and head drift isolate unified verification without suppressing configured automation or generic CI events.

Reviewer question Can one repository or evidence source stop sibling repositories or low-level events?

  • Which failures are connector-fatal, and which stay repository- or path-scoped?
  • Does a Relay outage retry delivery without changing the connector’s low-level event stream?

Invariant: Authentication remains connector-fatal; other failures stay repository- or path-scoped.

07 / extension seam

A seam, not an engine

The event and notification contracts remain generic enough for a future durable aggregation family, but no projection engine is built without a second use case.

Reviewer question Does the connector-owned first producer preserve a clean migration path without speculative machinery?

  • Can a later typed durable reducer consume correlated events without rewriting delivery?
  • What producer and idempotency semantics must be preserved or versioned at migration?

Invariant: Migration requires a new version or explicitly preserved producer and idempotency semantics.
